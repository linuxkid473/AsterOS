# Patch: xcrun SDK resolution + iig `-arch` rejection

**Problem 1 — `xcrun -sdk <path>`:** xnu's `README.md` examples always use short SDK names (`SDKROOT=macosx.internal`). Internally, `makedefs/MakeInc.cmd` hardcodes `XCRUN = /usr/bin/xcrun` and calls `$(XCRUN) -sdk $(SDKROOT) ...` to resolve the SDK path/version and to find every build tool (clang, mig, iig, strip, lipo, ctfconvert, ...). We need `SDKROOT` to be our own local, header-patched copy of the SDK (`build/SDKs/MacOSX10.15.sdk`, since no real Catalina SDK exists on this host), but the real `/usr/bin/xcrun -sdk <arbitrary path>` refuses to resolve an unregistered path on this Xcode/macOS version ("SDK ... cannot be located").

**Fix:** `build/tools/bin/xcrun` — a wrapper script that recognizes `-sdk <our SDK path>` and answers `-show-sdk-path`/`-show-sdk-version` directly, and forwards `-find <tool>` (and anything else) to the real xcrun using the real `macosx` SDK, since the actual toolchain binaries don't depend on which sysroot we're compiling against. Since `XCRUN` is a hardcoded absolute path in the makefile (not looked up via `$PATH`), it's wired in via `make XCRUN=$(pwd)/build/tools/bin/xcrun ...` on the command line (plain `=` assignments in the makefile are overridden by command-line variables in GNU Make, so this works without touching xnu source).

**Problem 2 — `iig`:** Building DriverKit headers (`iokit/DriverKit/Makefile`) invokes `iig` with `-arch x86_64` (via the generic `ARCH_FLAGS_X86_64` makedefs variable, used everywhere in the build). The `iig` shipped with this modern Xcode rejects that combination outright: `error: -arch, and -triple arguments are not permitted`, even though plain `clang` invocations elsewhere in the same build accept `-arch` fine.

**Fix:** In `iokit/DriverKit/Makefile`, changed just that one invocation's `$($(addsuffix $(CURRENT_ARCH_CONFIG),ARCH_FLAGS_))` to `-target unknown-apple-macos10.15` — this project only ever builds X86_64, so hardcoding here doesn't lose generality we need. Left `ARCH_FLAGS_X86_64` itself untouched since regular clang compiles throughout the rest of the build depend on it working as `-arch x86_64`.

Iterated through the exact error message each time (`iig` is unusually picky about this, being built on its own clang CompilerInvocation/LibTooling parsing rather than the normal driver): `-arch x86_64` alone → "-arch, and -triple arguments are not permitted"; `-target x86_64-apple-macos10.15` → "-target is only permitted with an unknown arch"; `-target unknown-apple-macos10.15 -arch x86_64` together → back to the first error. Only `-target unknown-apple-macos10.15` alone (arch component literally the string "unknown", letting iig fill in the real arch itself) works.
